# AWS Deployment Guide

This guide outlines the step-by-step process for provisioning the AWS infrastructure and deploying the API and Web applications using Terraform and GitHub Actions.

---

## 📋 Prerequisites

- An AWS Account with Administrator-level console access (non-root IAM User recommended).
- [Terraform CLI](https://developer.hashicorp.com/terraform/downloads) (v1.8.0 or newer).
- [Node.js](https://nodejs.org/) (v22) and [pnpm](https://pnpm.io/) (v9).
- [Docker](https://www.docker.com/) (running locally to build/test if needed).
- A GitHub repository containing the codebase.

---

## 🔐 Phase 1: Configure AWS IAM OIDC Trust (GitHub Actions Auth)

To allow GitHub Actions to securely deploy to AWS without using static, long-lived access keys, configure an OpenID Connect (OIDC) identity provider.

### 1. Register OIDC Identity Provider in IAM

1. Open the AWS Console and go to **IAM** ➔ **Identity Providers** ➔ **Add provider**.
2. Select **OpenID Connect**.
3. **Provider URL**: `https://token.actions.githubusercontent.com` (click "Get thumbprint" to verify).
4. **Audience**: `sts.amazonaws.com`
5. Click **Add provider**.

### 2. Create the GitHub Deployer IAM Role

1. In IAM, go to **Roles** ➔ **Create role**.
2. Select **Custom trust policy** and paste the following policy (replace `<AWS_ACCOUNT_ID>` and `<GITHUB_USERNAME>` with your details):
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Principal": {
           "Federated": "arn:aws:iam::<AWS_ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
         },
         "Action": "sts:AssumeRoleWithWebIdentity",
         "Condition": {
           "StringEquals": {
             "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
           },
           "StringLike": {
             "token.actions.githubusercontent.com:sub": "repo:<GITHUB_USERNAME>/smoke-tracker-cloud-dashboard:*"
           }
         }
       }
     ]
   }
   ```
3. Attach permissions to this role containing ECR, ECS, S3, and CloudFront permissions (a custom policy containing ECR push, ECS service updates, S3 sync, and CloudFront cache invalidation is recommended).
4. Save the role and copy its **ARN** (e.g., `arn:aws:iam::123456789012:role/github-actions-deploy-role`).

## 🛠️ Phase 2: Provision Infrastructure with Terraform

Because your Docker image registry and S3 bucket must exist before GitHub Actions can deploy code to them, you must run the initial Terraform setup locally.

1. Navigate to your desired Terraform environment directory (e.g., the cost-optimized `live-demo` to save ~77% on hosting, `production-reference` for enterprise-grade architecture, or the serverless `serverless-demo` environment to save ~86% on compute/load balancer costs):

   ```sh
   # For cost-optimized ECS hosting:
   cd infra/terraform/environments/live-demo

   # OR for enterprise-grade reference ECS architecture:
   cd infra/terraform/environments/production-reference

   # OR for the ultra-low-cost serverless architecture (AWS Lambda + API Gateway):
   cd infra/terraform/environments/serverless-demo
   ```

2. Create your local variables file:
   ```sh
   cp terraform.tfvars.example terraform.tfvars
   ```
3. Edit `terraform.tfvars` and set:
   - `aws_region` (e.g., `us-east-1`)
   - `project_name` (e.g., `smoke-tracker-cloud-dashboard`)
   - `api_image` (e.g., `<AWS_ACCOUNT_ID>.dkr.ecr.<REGION>.amazonaws.com/smoke-tracker-cloud-dashboard-api:latest`)
   - `database_password` (a strong master database password)
4. Authenticate your terminal to AWS using access keys from your IAM User:
   ```sh
   export AWS_ACCESS_KEY_ID="your_access_key_id"
   export AWS_SECRET_ACCESS_KEY="your_secret_access_key"
   export AWS_DEFAULT_REGION="us-east-1"
   ```
5. Initialize and apply the configuration:

   ```sh
   terraform init
   terraform plan
   terraform apply
   ```

   _Note the outputs generated by Terraform upon success._
   - **`live-demo` Topology (Cost-Optimized ECS):** Runs ECS tasks in public subnets with public IPs using Fargate Spot. Egress to ECR, logs, and secrets goes directly via the Internet Gateway (free), saving ~$86/month by eliminating Interface VPC Endpoints.
   - **`production-reference` Topology (Enterprise-Grade ECS):** Runs ECS tasks in private subnets with no public IP. The tasks do not use a NAT Gateway; image pulls, runtime secrets, and logs are accessed securely via private Interface VPC endpoints.
   - **`serverless-demo` Topology (Ultimate Serverless Low-Cost):** Runs backend Fastify API on AWS Lambda and API Gateway (HTTP API), completely eliminating the load balancer (ALB) and ECS Fargate. The database remains securely in private subnets, and static assets are served via CloudFront + S3. Saves up to **87%** in monthly baseline costs.

## ⚙️ Phase 3: Configure GitHub Secrets & Variables

In your GitHub Repository, navigate to **Settings** ➔ **Secrets and variables** ➔ **Actions**.

### 1. Repository Secrets

| Secret Name           | Description / Value                             |
| :-------------------- | :---------------------------------------------- |
| `AWS_DEPLOY_ROLE_ARN` | The ARN of the IAM OIDC Role created in Phase 1 |

### 2. Repository Variables

| Variable Name                | Description / Value                                                                  |
| :--------------------------- | :----------------------------------------------------------------------------------- |
| `ENABLE_AWS_DEPLOY`          | Set to `true` to enable deployment workflows                                         |
| `AWS_REGION`                 | The target region (e.g., `us-east-1`)                                                |
| `ECR_REPOSITORY_URL`         | ECR repository URL from Terraform output                                             |
| `ECS_CLUSTER`                | ECS cluster name (default: `smoke-tracker-cloud-dashboard-cluster`)                  |
| `ECS_SERVICE`                | ECS service name (default: `smoke-tracker-cloud-dashboard-api`)                      |
| `FRONTEND_BUCKET`            | S3 frontend bucket name                                                              |
| `CLOUDFRONT_DISTRIBUTION_ID` | CloudFront distribution ID                                                           |
| `VITE_API_BASE_URL`          | The public Load Balancer (ALB) URL (e.g., `http://smoke-tracker-cloud-dash-api-...`) |

## 🔑 Phase 4: Populate AWS Secrets Manager (Runtime Configuration)

The API pulls database secrets and tokens at runtime from AWS Secrets Manager. The secret shells are created by Terraform, but the values must be populated manually.

In the `production-reference` environment, ECS retrieves these secrets over the private Secrets Manager VPC endpoint. In the `live-demo` environment, ECS retrieves them securely over the internet via the Internet Gateway. In the `serverless-demo` environment, Terraform resolves these secrets at deploy-time and injects them as plaintext environment variables into the Lambda configuration.

Go to the **AWS Secrets Manager** console, select the created secrets, and enter the following values:

1. **`smoke-tracker-cloud-dashboard/database-url`**: Set to the Prisma connection string:

   ```text
   mysql://<DB_USER>:<DB_PASSWORD>@<RDS_HOSTNAME>:3306/smoke_tracker
   ```

   - `<DB_USER>`: The database username (default: `smoke_admin`)
   - `<DB_PASSWORD>`: The password set in `terraform.tfvars`
   - `<RDS_HOSTNAME>`: The hostname/endpoint of your Amazon RDS instance (can be found in the RDS console or under the terraform resource state).

2. **`smoke-tracker-cloud-dashboard/jwt-secret`**: Set to a secure, random 32+ character key. (This will be shared as the `ACCESS_TOKEN_SECRET` and `REFRESH_TOKEN_SECRET` environment variables in ECS).

## 🚀 Phase 5: Run Deployments

### Run GitHub Actions Deployments (ECS Environments)

Go to the **Actions** tab of your repository, select **Deploy API** and **Deploy Web** from the sidebar, and trigger both manually using the **Run workflow** dropdown (on the `main` branch).

_(Note: For ECS, database migrations run automatically on API startup, so no manual database execution step is required)._

### Deploying to AWS Lambda (Serverless Environment)

For the `serverless-demo` environment, the deployment pipeline updates the Lambda functions instead of an ECS Service:

1. Build and push the API container image to ECR.
2. Update the **Migration Lambda** function code to use the newly pushed ECR image tag:
   ```sh
   aws lambda update-function-code --function-name "smoke-tracker-cloud-dashboard-migration" --image-uri "$ECR_REPOSITORY_URL:latest"
   aws lambda wait function-updated-v2 --function-name "smoke-tracker-cloud-dashboard-migration"
   ```
3. Invoke the **Migration Lambda** to execute Prisma database migrations:
   ```sh
   aws lambda invoke --function-name "smoke-tracker-cloud-dashboard-migration" response.json
   ```
4. Update the primary **API Lambda** function code to use the newly pushed ECR image tag:
   ```sh
   aws lambda update-function-code --function-name "smoke-tracker-cloud-dashboard-api" --image-uri "$ECR_REPOSITORY_URL:latest"
   aws lambda wait function-updated-v2 --function-name "smoke-tracker-cloud-dashboard-api"
   ```

### Seeding the Serverless Database

Since migrations run in a VPC-private Lambda function and the database is private, you cannot run `pnpm db:seed` locally. Instead, the migration Lambda wrapper script supports database seeding via invoke payloads:

```sh
aws lambda invoke \
  --function-name "smoke-tracker-cloud-dashboard-migration" \
  --payload '{"action": "seed"}' \
  --cli-binary-format raw-in-base64-out \
  response.json

cat response.json
```
